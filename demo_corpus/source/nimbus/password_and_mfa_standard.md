# Password and MFA Standard

## 1. Purpose

This standard defines the minimum requirements for passwords, passphrases and multi-factor authentication (MFA) on all Nimbus systems. It implements the access control section of the *Information Security Policy* and follows current NIST SP 800-63B guidance, which favours long passphrases and MFA over frequent forced changes.

## 2. Scope

All user accounts on Nimbus systems: single sign-on (SSO) identity, email, laptops, VPN, cloud consoles (AWS, Azure, GCP), source control, NimbusOps production access and any SaaS tool used for Nimbus work. Client-provided accounts follow the client's rules if they are stricter.

## 3. Password requirements

### 3.1 User passwords

| Requirement | Value |
|---|---|
| Minimum length | 14 characters |
| Maximum length | At least 64 characters supported |
| Complexity rules | None enforced; passphrases of 4 or more random words are encouraged |
| Blocked passwords | Checked against a list of breached and common passwords, and words such as "Nimbus", "Pune", "Hinjewadi" and the user's name |
| Password history | Last 5 passwords cannot be reused |
| Expiry | No scheduled expiry; rotation only on compromise |
| Failed attempts | Account locked for 15 minutes after 10 failed attempts |

### 3.2 When a password must be changed

Passwords are **not** rotated on a schedule. You must change a password immediately when:

1. You suspect it has been seen, phished or guessed.
2. It appears in a breach notification raised by the SOC.
3. You shared it by mistake (for example, typed into a chat window).
4. IT or the SOC instructs you to.

### 3.3 Administrative and privileged accounts

- Minimum length of 20 characters, generated by the password manager.
- Separate admin accounts (prefix `adm-`) are used for privileged work; normal accounts are never given admin rights.
- Privileged access to production (including NimbusOps on AWS) is granted just-in-time for a maximum of 8 hours through the privileged access management tool, with ticket reference.

### 3.4 Service accounts and secrets

- Service account credentials are at least 32 random characters, stored only in the secrets manager.
- Secrets are rotated every 90 days and immediately on staff exit from the owning team.
- API keys in code repositories are detected by pre-commit and pipeline scanning; a detected secret is treated as compromised and rotated within 24 hours.

## 4. Multi-factor authentication

### 4.1 MFA is mandatory

MFA is **mandatory for every user on every system that supports it**, without exception. Systems that cannot support MFA must sit behind SSO or VPN that does.

### 4.2 Approved factors

| Factor | Allowed for | Notes |
|---|---|---|
| FIDO2 hardware security key | All users; required for admins and SRE | Issued by IT, 2 keys per admin |
| Nimbus Authenticator push with number matching | All users | Default factor |
| TOTP code from authenticator app | All users | Backup factor |
| SMS one-time password | Not allowed | Except for initial recovery with IT verification |
| Email one-time password | Not allowed | — |

### 4.3 Enrolment

New joiners enrol MFA on day 1 with IT. A user must register at least two factors (for example, push plus TOTP) so that the loss of one phone does not lock them out.

### 4.4 Lost factor or new phone

1. Raise a ServiceDesk ticket or call extension 4357.
2. IT verifies identity by video call against the HRMS photo and a manager confirmation.
3. A temporary access pass valid for 1 hour is issued to re-enrol.

## 5. Password managers

Nimbus provides an enterprise password manager to all employees. Use it to generate and store all work passwords. Browser-built-in password storage is disabled on managed laptops. Storing passwords in spreadsheets, notes apps or plain text files is prohibited.

## 6. Single sign-on

All new SaaS applications must integrate with Nimbus SSO before going live. Exceptions require CISO approval and are reviewed every 6 months.

## 7. Monitoring

The SOC monitors for impossible-travel logins, MFA fatigue (more than 3 rejected push prompts in 10 minutes), and logins from anonymising networks. Any of these triggers an automatic session revoke and a SEV3 security ticket.

## 8. Responsibilities

| Role | Responsibility |
|---|---|
| All users | Follow this standard, report suspected compromise immediately |
| IT ServiceDesk | Enrolment, resets, identity verification |
| SOC | Monitoring and response |
| CISO | Owns this standard and approves exceptions |

## 9. Non-compliance

Accounts that do not meet this standard are disabled until fixed. Wilful sharing of credentials is a breach of the *Acceptable Use Policy*.
